    How the baseline was built

    estimate → budget

    A baseline is only as good as the estimate behind it. This bridge walks the award-stage engineer’s estimate down through value engineering, bid climate and buyout to the budget being controlled today — because a controls manager who inherits a baseline should be able to defend how it was set, not just measure against it.

    Estimate at completion — four methods

    EAC is not one number. Which formula you quote is a judgement about what the remaining work will behave like, and a controls manager should show the spread rather than pick one silently.

    Contingency vs. progress

    Drawdown should trail earned progress. When the drawdown line crosses above the progress line, the program is consuming reserve faster than it is producing value — the earliest reliable signal of a reset.

    Forecast reliability

    is the forecast trustworthy?

    A single EAC answers “what will this cost.” It cannot answer the question that actually matters to a program director: is this forecast getting more trustworthy over time, or less — and how far off was last month's prediction from what actually happened? Both are checkable, and neither shows up if you only ever look at today's number.

    EAC trend — last 6 reporting periods

    A forecast that oscillates is noisy but healthy. A forecast that moves the same direction every single period is not stabilizing — it is diverging, and the trend line is the only way to see that before it is obvious.

    1-month-ahead forecast accuracy

    Grades the forecasting method, not the program: what a simple run-rate projection said last month's actual cost would be, versus what it actually was. This is expected to be wrong sometimes — a scorecard that is never wrong is not measuring anything.

    Monthly spend rate — planned vs. actual

    Everything else on this tab is cumulative, which smooths out exactly the acceleration or deceleration a program director needs to see. This is the same S-curve data, one month at a time instead of running total.

    What-if model

    forecasting

    Drag the performance indices and watch the forecast move. This is the conversation a controls manager has with a program director: not “we are over”, but “here is what it costs if nothing changes, and here is the efficiency we would have to hit to land on budget.”

    Save up to four scenarios to compare the conversations side by side — “do nothing” against “recover the tunnel” against “draw contingency now”.

    The forecast is a distribution, not a point

    monte carlo

    A single EAC pretends to a certainty the data does not contain. This runs 4,000 simulated completions: each control account’s remaining work is priced at a future efficiency drawn around its observed CPI — downside wider than upside, because cost efficiency on capital work recovers slowly and degrades fast. Fixed seed, so the distribution is reproducible and testable.

    A second lens on the same question

    The Monte Carlo run above answers "given how this program has actually performed, what's the range of honest outcomes?" — it forward-simulates from this ledger's own observed efficiency. Reference class forecasting asks a different question: "how have similar completed programs, elsewhere, actually turned out?" Bent Flyvbjerg's database of 16,000+ megaprojects found rail projects run 45% over budget on average, fixed-link (bridge/tunnel) projects 34%, and roads 20% — overruns that are prevalent and predictable, not random noise. The two techniques are complementary, not competing: one grounds a forecast in this program's own track record, the other checks it against the base rate for programs of this type. A forecast that only does the first can still be optimistic in a way an entire asset class already tells you to expect. (Bent Flyvbjerg's published megaproject research, via PMI's research summary, verified 19 Aug 2026 — a real, external citation, not this program's own data.)

    Float is the early-warning system

    DCMA

    Cost variance tells you what already happened; total float tells you what is about to. Negative float means the package is driving the program completion date — recovery anywhere else does not move it.

    Total float by package (working days)

    Critical Path Length Index

    CPLI = (remaining duration + total float) ÷ remaining duration. Below 1.00 the path cannot absorb any more slip; DCMA flags below 0.95.

    Milestone variance

    Why SPI alone will mislead you

    Schedule Performance Index is measured in dollars of earned value, not days. It drifts back toward 1.00 as a program completes — even one finishing late — because earned value converges on budget regardless of when the work lands. It also cannot distinguish work on the critical path from float-rich work.

    That is why this framework pairs every SPI reading with CPLI (is the driving path still achievable?) and BEI (are activities actually completing on plan?). Three numbers, three different failure modes.

    A real, verified requirement behind this DCMA framing

    Sound Transit's own 2023 Standard Division 01 Specifications require prime contractors to schedule in Oracle Primavera P6 — Section 01 32 13.25, “Scheduling of Work” (the sub-$10M design-bid-build variant; sibling sections 01 32 13.10/.15/.20 cover larger and design-build contracts). This tab's own DCMA-style logic — CPLI, BEI, float erosion — is built from the same real methodology those specifications require, independently re-verified directly against the primary specification document, not cited secondhand.     Delivery health

    productivity · document control

    Cost and schedule indices are lagging indicators — by the time CPI moves, the money is spent. These are the leading ones: they move weeks earlier and they are the levers a controls manager can actually pull.

    Productivity factor by package

    Earned hours ÷ actual hours. Below 1.00 means the crews are burning more hours than the estimate carried — visible weeks before it reaches CPI.

    Document control aging

    RFI and submittal turnaround are the earliest signals of a design-phase problem, and the most common root cause of a later claim.

    Safety & compliance

    The one metric that can stop the job independent of cost or schedule — and its trend moves with acceleration pressure.

    Funding vs. spend

    Grant drawdown should track expenditure. Spending ahead of drawdown is a cash-flow exposure; drawing ahead of spend is a compliance one.

    Crew cost-per-hour

    weekly · leading indicator

    Cost per hour translates a crew's labor, equipment and overhead into a burn rate and checks it weekly against a standard — the same discipline behind CPH reporting on a manufacturing shop floor, applied to a field crew. It surfaces a problem days before it shows up in the control account's own CPI, and because it is tracked weekly rather than monthly, it can isolate why the burn rate moved, not just that it did.

    Data pipeline · guardrails · AI narrative

    How the numbers get here — and why leadership can trust them

    Every figure on this dashboard traces to a raw record through SQL anyone can re-run. The pipeline is deterministic (same rows in, same ledger out), guarded by checks that fail the build before a bad number can travel, and the AI layer writes prose only — it never touches a number.

    Pipeline architecture

    This is not a drawing of a hypothetical. The same model runs in this repository: pipeline/run_pipeline.py synthesizes the raw monthly claims deterministically, builds the ledger through fct_control_account.sql in DuckDB, and proves the result identical to what this page computes in JavaScript — 54 checks, two independent stacks, one set of numbers. That equality is the integrity argument.

    The model — fct_control_account.sql

    with monthly as (
  select package_id,
         sum(pv_delta) as pv,
         sum(ev_delta) as ev,
         sum(ac_delta) as ac
  from stg_progress_claims
  where claim_month <= date '2026-07-31'  -- data date, explicit
  group by package_id
)
select m.package_id, b.bac, m.pv, m.ev, m.ac,
       m.ev - m.pv                     as sv,
       m.ev - m.ac                     as cv,
       m.ev / nullif(m.pv, 0)          as spi,
       m.ev / nullif(m.ac, 0)          as cpi,
       b.bac / (m.ev / nullif(m.ac,0)) as eac,
       b.bac - ...                     as vac
from monthly m
join dim_control_account b using (package_id)

    Beyond this program · the real problem, not the synthetic one

    Connecting scattered, unclean, real-world data

    Everything else on this dashboard runs against one clean, synthetic ledger. A real capital program doesn't have that luxury — its data lives across six-plus systems that were never designed to agree with each other. This tab is the plan for that actual problem, grounded in the real AEC industry standard (ISO 19650 Common Data Environments, buildingSMART's IDS), not generic tech-industry terms: how to stage it, guard it, resolve disagreement between systems, and recover from errors proactively instead of just flagging them.

    The problem, stated plainly

    There's a specific, well-documented version of this: the Work Breakdown Structure (WBS) contractors use for project controls, and the Asset Breakdown Structure (ABS) transit agencies use for operations and maintenance, are organized around fundamentally different logic — work packages and spatial boundaries versus functional system topology. That mismatch is a documented, recurring cause of data loss at handover, not a one-off integration bug. The failure mode is rarely one dramatic error. It's the slow accumulation of small disagreements nobody resolved, until a report reaches a Board built on numbers that quietly stopped meaning the same thing across systems. The goal isn't “connect the systems” — it's making disagreement between systems something the process catches and resolves, not something a report silently averages over.

    Architecture — a governed staging pipeline, not a direct feed

    The AEC industry's own real, named version of "stage before trust" is the Common Data Environment (CDE) under ISO 19650 — four defined states, each requiring a specific approval gate before information can advance. The rule that matters most isn't the four states themselves — it's that nothing downstream ever reads a raw source directly, and nothing advances without its gate.

    Work in Progress

    Individual discipline teams develop models and documents. Unverified, visible only to the originating team.

    Shared

    Validated information exchanged across disciplines for coordination and clash detection — gated by technical verification.

    Published

    Fully authorized deliverables — the contractual baseline for procurement and construction — gated by client/agency formal authorization.

    Archived

    Immutable long-term record: as-built models, transaction history, audit trail — gated by final handover verification.

    A real, verified detail — not a hypothetical

    Sound Transit's own 2023 Standard Division 01 Specifications (Section 01 20 00.10, Appendix B, cost-reimbursable contracts) ties digital-tooling compliance directly to contractor pay: BIM/CAD software at $6.80/hr, non-CAD software at $0.86/hr, computer equipment at $0.60/hr — verified directly against the primary document, not cited secondhand. This kind of data governance already has a real dollar figure attached to it on a real transit agency's own contracts.

    One boundary worth being precise about: this billing-rate clause is a real, verified fact about a digital-tooling reimbursement rate. The CDE/ISO 19650 architecture above it is a separate thing — this program's own proposed staging framework, not something Sound Transit's contracts require or reference by name.

    Automated guardrails — machine-readable, not just described

    A real, small-scale version of buildingSMART's Information Delivery Specification (IDS) — an XML standard pairing applicability (which records a rule governs) with requirements (what those records must have) so a submittal that fails gets rejected with a specific, itemized reason. This dashboard's own 27-check integrity gate is a working small-scale version of the same pattern.

    When systems disagree

    Most reporting tools skip this entirely. The actual process, step by step — and the loop back at the end is the part that matters most: every novel discrepancy a person resolves should make the next occurrence of the same problem automatic.

    Proactive error recovery

    Detecting a problem and recovering from one are different capabilities. Most tools only do the first.

    Circuit breakers

    If a source feed starts failing validation repeatedly, stop trusting it automatically — fall back to last known-good with a visible staleness flag, rather than letting bad data keep propagating. The same instinct as this dashboard's own Gate 5 hard stop, applied to ingestion instead of governance.

    Quarantine, not silent drop or pass

    A record that fails validation doesn't disappear or pass through anyway — it goes to a visible quarantine lane with the specific reason it failed.

    Self-healing for known patterns

    Some errors have one obvious fix — a known unit-of-measure mismatch, a predictable timing offset. Auto-correct those narrowly and log that it happened.

    Already proven at small scale, here

    The integrity gate, the escalation matrix, the Actions register's stale-flag, and Gate 5 are all working instances of this same philosophy — on one synthetic ledger. This plan is the same architecture, at the scale a real program needs.
